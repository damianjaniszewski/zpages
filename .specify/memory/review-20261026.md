## 2. Findings in the current code

High:

1. `handlers-support.go:14-118`: the action handlers never check the
   method, and both consumers route OPTIONS to them. A CORS preflight or a
   scanner sending OPTIONS to `crash` kills the pod; OPTIONS to `fail`
   makes the kubelet restart it. Confirmed by a test.
2. `handlers-support.go:172-202, 344-348`: no authentication,
   `Access-Control-Allow-Origin: *` on every response, and `/env` returns
   the whole environment. Anyone on the pod network can read secrets
   from environment variables or silence logs with a log level change.
   The headers were confirmed by a test; the exposure is from reading.

Medium:

1. Data races. `Healthz` locks only the health mutex but marshals the
   whole `ServiceStatus`, readiness fields included; `Readyz` does the
   opposite. The support handlers marshal without any lock. `setLogLevel`
   writes `Logger.Level` without the atomic access logrus uses. Confirmed
   with `-race`.
2. `handlers-probes.go`: the probes write the response while their mutex
   is locked, so a slow client blocks the setters. From reading.
3. `handlers-support.go:120-158, 92-98`: `SetNotReady` and `UnsetNotReady`
   clear the forced-not-ready flag, and `SupportRestart` calls
   `UnsetNotReadyForced`. Application code or `/restart` silently undoes
   an operator's quiesce. Confirmed by a test.
4. `handlers-support.go:74`: `quit` sends on `ShutdownChannel` with a
   blocking send. A nil channel makes the request hang after readiness
   has already failed. Confirmed by a test.
5. Every `fmt.Fprintf(w, string(out))`: the JSON body is the format
   string. An environment value such as `50%` or a GUID with `%` produces
   invalid JSON. `go vet` fails on this and on copied mutexes. Confirmed.
6. `go-fibo.go:201`, `rest-collector.go:229`: the consumers listen only
   for `os.Interrupt`, while Kubernetes sends SIGTERM. The process dies
   without draining. From reading.
7. `zpages.go:66`, `handlers-probes.go:25-37`: `statusHealth` is never set
   to false, the forced-ok flags are never set, and nothing undoes `fail`.
   The 503 health branch and both 203 branches are dead code. Forced
   failure returns 501, which monitoring reads as "not implemented". From
   reading, checked with grep.

Low:

1. `quit` and `crash` exit before the response is flushed; callers always
   see EOF. Confirmed in a subprocess test.
2. `SupportLogLevel`: invalid JSON returns 200, a read error returns 204
   with a body, unknown levels are echoed back while the logger falls
   back to INFO, and the body size has no limit. Mostly confirmed.
3. `SupportEnv` splits each entry on every `=`, so values with `=` are
   cut. Confirmed.
4. `UnsetNotReadyForced` reports `ready` without checking `statusReady`,
   and `Updated` is never refreshed. Confirmed.
5. `Init`: a nil logger panics, the log level is not applied to the
   logger, a second call appends the application to its own dependencies
   again, and it overwrites the `ServiceStatus` both consumers build.
   Confirmed.
6. No `go.mod`, no tests, `gofmt` reports `zpages.go`.

## 3. Similar projects

Probe libraries in Go:

1. `alexliesenfeld/health`: synchronous and periodic checks, a 1 second
   result cache, timeouts, configurable codes. MIT, active.
2. `hellofresh/health-go` v5: checks run concurrently on each request,
   with per-check timeouts and OpenTelemetry spans. Apache-2.0, active.
3. `AppsFlyer/go-sundheit`: asynchronous checks with initial delay,
   period and timeout, plus listeners. Apache-2.0, active.
4. `k8s.io/apiserver` healthz and `controller-runtime` healthz: named
   checkers, `/livez` and `/readyz`, `?verbose` and `?exclude`, failure
   reasons kept out of responses. Apache-2.0, active.
5. `google.golang.org/grpc/health`: the application pushes a status per
   service, with `Shutdown` and `Resume`. Apache-2.0.
6. `heptiolabs/healthcheck` (now `vmware-archive`) and
   `InVisionApp/go-health`: archived.
7. `nelkinda/health-go`: implements the IETF draft; small and early.

None of these libraries has operator endpoints such as quiesce, fail or
runtime log level. The closest are gRPC `Shutdown` and `Resume`, and the
Kubernetes API server's shutdown delay. The probe side of `zpages` could
be replaced by a library; the operator side has no direct counterpart.

## 4. Standards and conventions

1. Kubernetes probes: codes from 200 to 399 succeed, only the code
   matters, the body is read up to 10 KiB, `timeoutSeconds` is 1 and
   `failureThreshold` is 3 by default. Liveness failure restarts the
   container, readiness failure removes the pod from EndpointSlices, and
   liveness and readiness probes wait until the startup probe succeeds.
2. Kubernetes API server: `/healthz` is deprecated since v1.16 in favour
   of `/livez` and `/readyz`. `?verbose` is for people; machines read
   the code.
3. IETF draft "Health Check Response Format for HTTP APIs": revision 06
   is dated 2021-10-16 and has expired. Media type
   `application/health+json`, not in the IANA registry. Status `pass`,
   `warn` or `fail`; `checks` maps names to arrays of results.
4. gRPC health protocol: `UNKNOWN`, `SERVING`, `NOT_SERVING` and
   `SERVICE_UNKNOWN`; `Watch` streams changes.
5. Spring Boot Actuator: liveness and readiness are separate health
   groups. Liveness "should not depend on health checks for external
   systems". Environment values are masked by default, only `health` is
   exposed over HTTP by default, and `shutdown` is disabled by default.
   The loggers endpoint changes levels at runtime.
6. MicroProfile Health 4.0: `/health/live`, `/health/ready` and
   `/health/started`; 200 for up, 503 for down.
7. Graceful shutdown: on pod deletion the kubelet runs preStop and sends
   SIGTERM while the endpoint is removed, with a 30 second default grace
   period. Proxies and DNS update at different speeds, so an application
   keeps answering for a short delay before it stops. The API server's
   `--shutdown-delay-duration` fails `/readyz` at once and keeps
   `/livez` passing during the delay.
8. Kubernetes notes that a readiness probe is not needed to drain on pod
   deletion, because the endpoint is removed anyway. Failing readiness on
   SIGTERM matters most for external load balancers and for an operator
   drain such as quiesce.
9. Logging: `slog.LevelVar` changes a handler's level at runtime. zap's
   `AtomicLevel` has an HTTP handler with GET and PUT, a precedent for
   the log level endpoint.

## 5. The name

1. In OpenCensus, zPages are in-process HTML pages for RPC statistics and
   traces, at `/rpcz` and `/tracez`. OpenCensus is archived.
2. The OpenTelemetry Collector has a zpages extension with ServiceZ,
   PipelineZ, ExtensionZ, FeatureZ and TraceZ pages.
3. So in the observability world the name means debug pages for traces
   and RPCs, not health and admin endpoints. Whether to rename is an
   open decision.

## 6. Platform notes to verify

1. GKE: Ingress with container-native load balancing builds its health
   check from the readiness probe; Gateway uses `HealthCheckPolicy`;
   pods behind network endpoint groups get a readiness gate.
2. Istio sidecar mode: probes are rewritten to go through the Istio
   agent; an application that calls out before its sidecar is ready gets
   errors; a sidecar that stops first drops in-flight calls. Kubernetes
   native sidecar containers fix the order.
3. Istio ambient mode: generally available since 1.24; a node-level proxy
   gives transport-level metrics, and request-level metrics need a
   waypoint proxy.
4. Trace headers that applications must pass on for Istio, such as
   `x-request-id`, `traceparent`, `tracestate` and the `x-b3-*` set.

## 7. Assumptions examined

1. "Sidecars collect metrics and inject tracing headers." The sidecar
   records request metrics and starts traces, but only the application
   can connect an inbound request to its outbound calls by passing the
   headers on. Ambient mode without a waypoint gives no request-level
   metrics, so the application's own state metrics matter more.
2. "Readiness should fail when a dependency is down." Only when the
   dependency belongs to this pod. A shared dependency failing would take
   every pod out of rotation at once.
3. "Distinct status codes tell the platform more." They do not; the
   kubelet sees success or failure. Detail belongs in the body and in
   metrics.
4. "Failing readiness is how a pod drains." On pod deletion the endpoint
   goes anyway. Failing readiness first matters for external load
   balancers and operator drains.
5. "Admin endpoints are safe inside the cluster." The pod network is
   reachable from every pod, and `Access-Control-Allow-Origin: *` lets a
   browser page reach a port-forwarded endpoint.
6. "Consumers can route the handlers." Both consumers routed OPTIONS to
   the actions; the library should own its routes.

## 8. Ideas for future work

1. Use the IETF `checks` shape for upstream status, filled by background
   checks with timeouts.
2. Drive quiesce, resume and SIGTERM through one state machine, and feed
   a gRPC health service from the same state.
3. Switches that reproduce common mistakes, for demonstrations.
4. Rename the library if the clash with zPages confuses the audience.
5. Show the timing between kubelet, load balancer and mesh during a
   drain, since each has its own view of the pod for a few seconds.
